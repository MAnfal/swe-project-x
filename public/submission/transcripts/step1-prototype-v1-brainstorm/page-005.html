# Design brief — Project Grain (mid-fi, web app)

## Product in one paragraph
Codeowners in a large monorepo have lost visibility into how work in their domain
actually gets done. AI writes most of the code; individual PRs look fine in review;
the cost only becomes visible months later as accumulated architectural drift.
Grain gives a codeowner a time-scrubbable map of their monorepo so they can see what
happened in their packages over any window — while they were on vacation, or during a
sprint they weren't on — and how each change was built. It informs; it never blocks or
judges. The owner decides what to do with what they see.

## Two scenarios the UI must serve
1. A frontend feature quietly required a change inside the render engine. The render
   engine's owner wasn't on the call. The owner needs to notice that their package was
   touched — including indirectly — and see the approach that was taken.
2. An owner returns from two weeks away. They need to scrub to those two weeks and see
   every change that landed in their domain, grouped by feature, not by commit.

## Core interaction model: three levels of progressive disclosure on one infinite canvas

**Level 1 — Topology.** Nodes are the monorepo's apps and packages (e.g. `App 1`,
`Render Engine`, `Package 2`). Dependency edges exist in the data but are NOT drawn by
default — a monorepo with every edge drawn is an unreadable hairball. Packages touched
within the selected time window are rendered active; untouched ones are dimmed/grayed
to cut visual load. Each active node carries a badge showing how it was reached, e.g.
`4 direct · 2 via Package 2`. Focusing a node (hover or click) reveals only that node's
dependency neighborhood.

**Level 2 — Change clusters.** Expanding a package reveals one node per pull request
that touched it in the window, directly or transitively. Each node shows: a human
label for the change (e.g. "Added global site settings"), PR number, author, merge date,
which packages it spanned, and a one-line "approach" note describing *how* it was built
(e.g. "wired site settings directly into render config rather than through the existing
settings resolver"). The approach note is the highest-value content on the screen —
design it to be readable at a glance, not buried.

**Level 3 — How it was built.** Expanding a change reveals an ordered left-to-right
chain of steps, e.g. `Added a DB column → Added a resolver record → Changed render config
to accept settings`. Each step references the files involved.

## The time slider
Persistent, bottom of the canvas, spanning the full life of the repository —
conceptually like the Internet Archive's Wayback timeline. Requirements:
- Selects a **range** (two handles), not a point in time.
- Shows change volume over time as a histogram/sparkline behind the track, so an owner
  can see where activity clustered before they scrub.
- Quick presets: Last 7 days · Last 30 days · Last 90 days · All time.
- The selected range is always legible as explicit dates, and drives everything on the
  canvas above it.

## Screens and states to design
1. **Landing / repo selection.** A dropdown of pre-analyzed demo repositories, plus an
   `Other…` option. Selecting `Other…` replaces the dropdown *in place* with a GitHub
   repository URL input; a back arrow sits to the left of that input and restores the
   dropdown when clicked. Include the invalid-URL error state.
2. **Ingest progress.** Analyzing a live repo takes tens of seconds of sequential work.
   Needs streamed, specific progress ("Fetching pull requests… 42 of 100"), not a bare
   spinner.
3. **Canvas — Level 1**, with a window where several packages are active and most are dimmed.
4. **Canvas — Level 2**, one package expanded.
5. **Canvas — Level 3**, one change expanded into its step chain.
6. **Empty state** — the selected window contains no activity in this repo.
7. **Error state** — repo not found, rate-limited, or analysis failed.
8. **Onboarding overlay** — a short, dismissible first-run walkthrough (3–4 steps)
   teaching the slider and the three levels, with a way to replay it later.

## Navigation and canvas affordances
- A breadcrumb showing depth: `App 1 / Render Engine / Added global site settings`,
  each segment clickable to return to that level.
- Standard canvas controls: zoom in/out, fit-to-view, reset, minimap.
- Expanding and collapsing must be keyboard-operable, not click-only.

## Visual and technical constraints
- Built with Tailwind CSS + shadcn/ui on React Flow. Stay within what those compose
  naturally — custom React components inside graph nodes are fine; bespoke canvas
  painting is not.
- Dark theme is primary; light theme should be plausible from the same tokens.
- Desktop-first, designed for ≥1280px, degrading acceptably to 1024px. No mobile.
- Active vs dimmed state must not rely on color alone (opacity, weight, or border too).
- Information density is the core design problem here: the whole point is reducing
  overload, so every level should reveal only what that level answers.

## Explicitly out of scope
Chat or AI conversation UI, authentication, settings pages, mobile layouts, multi-repo
comparison, and any UI that blocks, gates, or approves a change. Grain reports; it
never gatekeeps.

## Deliverable
Mid-fidelity screens for all eight states above, annotated with interaction notes
(what expands, what dims, what the slider drives).
