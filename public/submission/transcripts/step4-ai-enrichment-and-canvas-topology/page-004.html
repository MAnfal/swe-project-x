Yes — public only, and it matters more than convenience here.

The SPEC scopes the product to "any public TypeScript monorepo" (SPEC.md:67), and the three curated repos are public. But the stronger reason is chunk 06's shape: it takes a visitor-supplied repository URL and fetches it with the server's token. That's a confused deputy. If the deployed token could read private repos, anyone who pastes a private repo URL the token happens to have access to gets its contents rendered back at them — pull request titles, commit messages, changed file paths.

Nothing in github.ts guards against that; it passes whatever token it's handed to the endpoints. The boundary is the token's own access, so public-only is what enforces it.

So: public read access only, on a token that can't see anything you'd mind a stranger reading. If your account has private repos, a fine-grained PAT scoped to "Public repositories (read-only)" is the safer of the two options — an unscoped classic token inherits your full account visibility for reads, which is fine locally but wrong for anything deployed.

Worth flagging as scope, not a request: chunk 06's plan bounds the fetch but I haven't seen it bound which repositories are allowed. I'll check whether it rejects non-public repos explicitly when that chunk comes up, rather than relying on the token alone — defence in depth for the one path that takes untrusted input.
